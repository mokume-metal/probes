# 0009 — 書き出したファイルの中身を、焼いた番号で読み戻す物差しを別に立てる

## 状態

採用 (2026-09-25)

## 文脈

mokume の書き出し (`save`・連番・`beginRecord` の `.mov`) について、mokume 自身の検査は
復号した絵と時刻の比較が中心である。次のものは見ていない。

- PNG の色の刻印
- 失敗が同じ撮る係の録画へ波及するか
- 同じ名前への書き出しの順序
- ファイルのバイトの一致

probes の物差しもどれも描画先の画素しか見ておらず、**ファイルになった後**を測っていなかった
(#26 の観点 3、#21 の調査)。

調べた結果、書き出しの大半は `swift test` の中で `SketchRuntime` (フレーム番号の時計) を回せば
測れる。止め方 (合図・`exit`)・孤児・世代の入れ替えだけは、窓を出す本物のプロセスが要る。

## 決定

**物差し `Imprint` を足す。** プロセスを操る物差し (Lifecycle、#21) とは分ける。

- **分ける理由。**
  - 測る対象 (ファイルの中身 ↔ プロセスの寿命) が違う。
  - 走らせ方 (窓なしで数秒 ↔ 窓を出して子プロセスを操る) も違う。
  - Imprint は既定の `swift test` で回せるが、Lifecycle はそうはいかない。
- **判定は、各フレームに焼いたフレーム番号を読み戻して行う。**
  - 番号は 16 個の升に白と黒で置く。
  - 灰色の両端だけを使うので、符号化の誤差にも色空間にも読みが左右されない。
  - 何枚目の絵が何枚、どの順で入ったかを、絵そのものから数えられる。
- **読み戻しは macOS 標準の口 (AVFoundation・ImageIO) だけで行う。** ffprobe などの外の道具に
  頼らない。
- **約束の出典が書かれているものだけを破れとして数える。** 連番の撮り直しで前の録りの
  ファイルが残る件は、約束が消すとは言っておらず、Processing とも同じなので、突かない。
- **稀にしか出ない破れは `withKnownIssue(isIntermittent: true)` で包む。** 出なかった回も
  赤くならないので、直ったことはこの物差し単独では知らせない。`scripts/stress.py` で反復し、
  既知の問題の件数のゆれで見る (ADR-0007)。
- **秒の境目でだけ出る破れは、毎回起きる形にしてから包む。** 2 本の書き出しの間を 1 秒以上
  あけて、たまたま一致する回を作らない。そのうえで、刻印を除いたバイトの一致を別に厳しく
  押さえる。
- **版は `v0.11.2` で始める。**

## 影響

- mokume `v0.11.2` で 10 件を突き、3 件が約束を破っていた。3 件とも Bug として起票した。
  - 録画中の `save` の 1 度の失敗で動画が途切れる (mokume#1626)
  - 同じ名前への `save` の順序が崩れる (mokume#1627)
  - `.mov` の容れ物の時刻でバイトが一致しない (mokume#1628)
- **後ろの 2 件は、1 回回すだけでは見えなかった。** `stress.py` で反復してはじめて見えた。
  ADR-0007 の道具が、新しい物差しでも効くことが分かった。
- Imprint の既知の問題の件数は 2 件だが、mokume#1627 が出た回は 3 件になる。`stress.py` の
  「件数のゆれ」はこの物差しでは想定内で、ゆれが消えたら mokume#1627 が直ったしるしとして
  読む。
