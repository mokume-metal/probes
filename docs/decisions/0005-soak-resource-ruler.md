# 0005 — 絵ではなく資源 (メモリ・時間・落ちる) を測る物差しを別に立てる

## 状態

採用 (2026-09-25)

## 文脈

Probe・Drift・Routine・Reach は、どれも**絵**を見る。約束どおりの画素が出るか、フレームを重ねて
ずれないか、よく使う口が描けるか。

作品を長く回したときに困るのは、絵が正しいまま次のことが起きる場合である。

- 1 枚ごとにメモリが増えて減らない。
- 仕事の量に見合わず重い。
- 極端な値でプロセスごと落ちる。

展示で数時間回す作品では、どれも絵より先に致命的になる。しかも 1 枚目の絵には出ないので、
どの物差しも正面から測っていなかった。

## 決定

**物差し `Soak` を足す。** 比べるのは絵ではなく、フレームを重ねたときの**増え方と時間**、
それに**落ちるかどうか**である。

- **既存の物差しに足さず、別の 1 本にする。**
  - 測る量が違う (画素 ↔ footprint・GPU の確保量・時間・終了の仕方)。
  - 閾値の置き方も違う。
  - 資源の値はプロセス全体の値なので、他の物差しの検査と同じプロセスで並べて回すと混ざる。
- **テストは窓と同じ条件で回す。** 毎フレームを `autoreleasepool` で包み、`Task.yield()` で
  main actor を譲る。
  - 譲らないと、mokume が GPU の完了を main actor の `Task` で後始末する作りのため、何もしない
    スケッチでも増え続ける。窓ではそれが起きないので、検査が作品と違うものを測ってしまう。
  - 譲らない回し方で増えることそのものは、別の候補 (`headlessAdvance`) として突く。
    `advance()` の説明は、誰がどう叩くかを外側に任せているため。
- **閾値は機械に依らない形で置く。**
  - メモリは、参照の経路 (同じ仕事を疑いの入らない書き方で) との増え方の差で見る。
  - 時間は、仕事を倍にしたときの比で見る。
  - 絶対の ms は機械で変わるので、閾値には使わない (立体の線だけは「1 フレームの 16 ms +
    線なしの 10 倍」という予算で見る。比べる相手が同じ機械の線なしなので、機械差はそちらに
    乗る)。
- **落ちる候補は exit test (子プロセス) に閉じ込め、窓には並べない。** 対照 (極端でない値) が
  通ることを先に押さえ、落ちたのが口のせいであることを示す。
- **1 経路 = 1 本のスケッチ、経路ごとに別の `SketchRuntime`** (ADR-0003 の Routine と同じ)。
  窓は資源の値を読むので、1 度に 1 経路だけ回す。

## 影響

- mokume v0.11.1 で 11 件の破れを見つけ、10 件を起票し、1 件を既知の Issue (mokume#1431) へ
  数字として足した。内訳はメモリ 4・時間 2・落ちる 4 (起票の単位で数える)。
- **時間の検査は debug 組みで回る。** `mokume run` と同じ条件だが、release より数倍遅い。
  比で見ているので判定は変わらないはずだが、release で速くなる類の改善は見えない。
- **footprint の読みには雑音がある。** malloc が空きをまとめて返す段や、領域を 1 度だけ伸ばす段を
  踏む。増え方は中央値どうしの差で測り、「増えていない」の閾値を 32 KB/枚まで緩めてある。
  1 枚あたり数 KB の小さな漏れは、`headlessAdvance` のように枚数を多く取らないと見えない。
