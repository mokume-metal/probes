# Imprint — mokume v0.11.2 が「書き出したファイルの中身」を突く

**作品ではなく物差しである。** 他の物差しが描いた絵 (描画先の画素) を見るのに対し、こちらは
**ファイルになった後の中身**を見る。対象は `save`・連番・`beginRecord` の `.mov` で、確かめる
ことは次のとおり。

- 頼んだフレームが何枚、どの順で入ったか
- 時刻の間隔
- 色の刻印
- 同じ入力から同じバイトが出るか

展示の記録や、書き出した絵をほかの仕組みへ渡す作品では、ここが崩れると絵が正しくても
成果物が壊れる。

## 何をしているか

**各フレームにフレーム番号を 2 値の升で焼き、書き出したファイルから読み戻す。**

- 左上の横 1 列、16 個の升に、番号の 2 進を白 (255) と黒 (0) で置く ([`Sources/Imprint/Ticker.swift`](Sources/Imprint/Ticker.swift) の `Stamp`)。
- 灰色の両端だけを使うので、符号化の誤差 (ProRes 4444 で最大 2 階調) にも、色空間の刻印にも読みが左右されない。灰色は原色の取り方によらない (mokume#911)。
- 動画のどのフレームが何枚目の絵か、欠け・重なり・順序の崩れを、絵そのものから数えられる。

書き出させ方と読み方は次のとおり。

- **窓を出さずに書き出させる。** `swift test` の中で `SketchRuntime` を組み、`draw()` から
  `save` / `beginRecord` / `endRecord` を呼ぶ。最後に `closePlugins()` で書き切らせる。
  時計はフレーム番号から導くので、n 枚目の時刻は (n − 1) / fps で、何度回しても同じになる。
- **読み戻しは macOS 標準の口だけで行う。** 動画は AVFoundation (`AVAssetReader` で全フレームと各時刻、形式の宣言)、PNG は ImageIO (刻まれた色空間のまま 8 ビットへ広げる)。
- 動画の検査は、ProRes 4444 を書けない機械では理由を名乗って飛ばす。

| 確かめ方 | 何を通るか | 何で見るか |
| --- | --- | --- |
| `mokume run .` | 窓。焼いている番号の升と動く円を見せ、スペースで `imprint-###.png` へ連番を撮る | 目で見る |
| `swift test` | 窓を出さない経路。書き出したファイルを読み戻す | 番号・時刻・バイトを数で比べる |

## 走らせる

```bash
mokume run .          # 窓で番号の升を見る
swift test            # 書き出して読み戻す (数秒)
```

**`swift test` は緑で終わる。** 破れていたものは `withKnownIssue` で包んであり、「既知の問題」
として数えられる (`v0.11.2` では 13 本のテストで 5 件。本来の検査で mokume#1627 が出た回は 6 件)。
このうち 3 件は、起票に貼った再現 (`Tests/ImprintTests/Repros/`) をそのまま走らせる `ReprosTests` の分である
(mokume#1626・#1627・#1628・[docs/filing.md](../docs/filing.md))。#1627 の再現は機械を混ませて 20 試行を繰り返すので、
ほぼ毎回出る。
`v0.14.0` では 13 本のテストで 2 件になる (mokume#1628 の本来の検査と再現の 1 件ずつ)。#1626 が直って包みを外したためで、
再現の 1 本は包みを外して残してあり、戻れば赤くなる。#1627 も `v0.14.0` で直った。`python3 scripts/stress.py --repeat 2`
の 12 回 (ふだん・検証レイヤ・4 本同時) で件数は 2 件のまま一度も揺れず、ほぼ毎回出ていた再現も出なかったので、
本来の検査と再現の包みを外した。

**mokume#1627 は稀にしか出なかった**ので、`v0.11.2` では `isIntermittent` で包んでいた。
- 出なかった回も赤くならない。そのため、直ったことはこの物差し単独では知らせない。
- `python3 scripts/stress.py Imprint` で反復すると、既知の問題の件数のゆれ (5 ↔ 6) として見えた。直ったことは、反復してゆれが消えることで確かめた (`v0.14.0`)。

## 結果 — mokume `v0.11.2`

**10 件を突いて、3 件が約束を破っていた。** `saveFailureKeepsMovie` (mokume#1626) と `sameNameSave` (mokume#1627) は `v0.14.0` で直り、
下の「約束どおりだったもの」の表へ移した (行は消さずに残す)。2 件は 1 回回すだけでは見えず、
`scripts/stress.py` で反復してはじめて見えた (ADR-0007)。

### 破れていたもの

| 鍵 | 何が起きたか | mokume |
| --- | --- | --- |
| `byteDeterminism` | 同じ入力から書き出した `.mov` は、秒の境目をまたぐと容れ物の作成・更新時刻 (`mvhd`・`tkhd`・`mdhd`) の 6 バイトだけが違う。説明の「ファイルのバイトまで一致」と食い違う。**刻印を除いたバイト (絵と時刻の表) は一致する**ことを別に押さえた | [#1628](https://github.com/mokume-metal/mokume/issues/1628) |

### 約束どおりだったもの

| 鍵 | 見たこと | 約束の出典 |
| --- | --- | --- |
| `recordRange` | 5 枚目で撮り始めて 25 枚目で止めると、動画は 5…24 の 20 枚。欠けも重なりも無い。直前の `save` も頼んだフレームの絵 | `beginRecord` の説明、mokume#1456 |
| `sequenceNumbering` | 連番は 0 から振られ、`##` で 100 枚を越えると桁が伸びる (`f-99` の次は `f-100`)。120 枚のどれも頼んだフレームの絵 | `beginRecord` の説明 |
| `ptsSpacing` (24・30・60 fps) | 時刻の間隔はどこも 1/fps (1/90000 秒の刻みで割り切れる)。長さは枚数 / fps | `MovieFile`、mokume#1457 |
| `ptsLate` | 128 秒を越えた所 (7690 枚目) から撮っても、間隔は 1500 刻み (1/60 秒) のまま。Float の時刻の粗さは出なかった | ADR-0025 決定 1 |
| `rerecordMovie` | 同じ `.mov` へ短く撮り直すと、中身は新しい録りだけ。置き場に一時ファイルも残らない | — |
| `pngColorTag` | PNG は Display P3 を刻む。`fill(204, 153, 0)` の生のバイトは (196, 155, 51)、灰色は数のまま | ADR-0011、mokume#911 |
| `movieMatchesPNG` | 同じフレームの動画と PNG の差は 2 階調以内。動画は ProRes 4444 で、原色 P3_D65・転送 sRGB・行列 709_2 を宣言する | ADR-0023 決定 2・4 |
| `saveFailureKeepsMovie` | 録画の最中に書けない先への `save` が 1 度失敗しても、動画は 40 枚そろう。**`v0.11.2` では** 3 フレーム後に撮る係ごと外れ、動画が途切れた (40 枚のはずが 15 枚)。静止画の失敗の印が消えないまま、差込口の健康として数えられたため | [#1626](https://github.com/mokume-metal/mokume/issues/1626) (`v0.14.0` で直った) |
| `sameNameSave` | 同じ名前へ毎フレーム `save` すると、最後に残るのが最後のフレームの絵とは限らない。1 プロセスずつで 600 試行に 1 回、4 本同時で 1200 試行に 12 回崩れた (残った絵は 21〜29 枚目) | [#1627](https://github.com/mokume-metal/mokume/issues/1627) (`v0.14.0` で直った) |

各検査は、疑いの側を壊すと赤くなることを確かめてある。壊し方は次の 4 通り。
- 1 枚だけ番号を焼き損ねる
- 色を変える
- 刻印を消さずに比べる
- fps をずらす

## 出口の取り合い — mokume `v0.16.2`

**描いた絵がどの出口 (窓・共有面・書き出し) へ行くか**を、窓が 2 枚以上絡む構成で突いた (#25)。
書き出したファイルの手前で、絵の行き先と後始末が他の窓に奪われる破れである。

突いた構成は次の 4 つ。
- watch の作品の窓とプレビュー
- 同じ場所で走らせた 2 本目のスケッチ
- watch の隣での書き出しと、窓なしの描画
- 1 プロセスに 2 つの `SketchApplication`

どれも標準入力・作業ディレクトリ・`NSApp`・プロセスの終わり方に触るので、再現 (`Tests/ImprintTests/Repros/`) を
exit test で子プロセスに閉じ込め、**終了コード 0 = 期待どおり・1 = 再現**で判定する。
4 件とも mokume の main (`00c8ba73`) でも出た。同じ機械で 3 回回して毎回出た。

`v0.16.2` では 17 本のテストで既知の問題が 6 件になる。従来の 2 件 (mokume#1628 の本来の検査と再現) に、この 4 件を足した。

### 破れていたもの

| 鍵 | 何が起きたか | 陰性対照 | mokume |
| --- | --- | --- | --- |
| `viewportTakeover` | `mokume watch A` が走る場所で、道具に起こされていないスケッチ B を走らせる。B は自分の窓を開かず、watch の目録 `surface.json` を自分の面で上書きする。watch の 2 枚の窓は B の絵を映し、B が終わっても B の最後の 1 枚で止まる。A を保存し直すまで戻らない | 区画が無い場所なら、B は自分の窓を開き、目録に触らない | [#2026](https://github.com/mokume-metal/mokume/issues/2026) |
| `renderBesideViewport` | `.mokume/viewport` が在る場所で書き出しを起こすと、標準入力が閉じている (/dev/null) だけで「道具が居なくなった」と読む。**0 / 30 枚**で終了コード 1 になる | 区画が無ければ 30 / 30 枚で 0 | [#2025](https://github.com/mokume-metal/mokume/issues/2025) |
| `stdinLeftNonBlocking` | `.mokume/viewport` が在る場所で `SketchRuntime` を作ると、標準入力に `O_NONBLOCK` を立てて戻さない。端末から回すと、終わった後に同じ端末で標準入力を読むプログラムが `EAGAIN` (Errno 35) で落ちる | 区画が無ければ立たない | [#2024](https://github.com/mokume-metal/mokume/issues/2024) |
| `secondApplication` | 1 プロセスで、`draw()` から 2 つ目の `SketchApplication.run()` を呼ぶ (第 2 窓の書き方)。2 つ目は 1 枚も描かない。**1 つ目が録っていた `.mov` に目次 (`moov`) が無く、開けない** | 2 つ目を作るだけで `run()` しなければ、`.mov` は開ける | [#2027](https://github.com/mokume-metal/mokume/issues/2027) |

上の 3 件は同じ根に見えるので、根の Issue [#2028](https://github.com/mokume-metal/mokume/issues/2028) で束ねた。「`.mokume/viewport` が在る = 道具に起こされた」と読み、起こした道具を確かめていない
(`SharedFrameSurface.isEnabled()`・`StandardInputEvents.makeIfDriven`)。

### 約束どおりだったもの

| 構成 | 見たこと |
| --- | --- |
| watch の 2 窓のうち片方を、不透明な窓で覆う・`orderOut` する | もう片方の窓と main は詰まらない (main の遅れは 9 ms 以内)。最小化・復元では 1 回 0.55 秒止まるが、mokume を含まない素の `NSWindow` でも同じで、AppKit の最小化の動きである |
| `.mokume/viewport` が在る場所の書き出しと窓なしの描画に、標準入力の管から出来事を流す | 混ざらない。60 枚の PNG が、流さない回とバイトで一致した |

外部画面が要る当たりは、画面が 1 枚の機械で測ったので突いていない。画面をまたいだ fps と、watch の子が `NSScreen.main` で歩調を取ることがそれにあたる。

## どうやって当たりを付けたか

mokume `v0.11.2` の書き出しの作り (`FrameRecorder`・`FrameWriter`・`MovieWriter`・`MovieFile`・
`PNGFile`) と、説明文・ADR-0023・ADR-0025 の約束を読んだ。そのうえで、**窓を出さずに
ファイルの中身から判定できる**当たりを選んだ (#21 の調査)。

### 当たりを付けたが突かなかったもの

| 当たり | 突かなかった理由 |
| --- | --- |
| 連番を同じパターンで短く撮り直すと、前の録りの後半のファイルが残って混ざる | 約束は「その録りの中で 0 から振る」までで、前の録りのファイルを消すとは言っていない。Processing の `saveFrame` も同じ振る舞いで、破れとは読めない |
| 止め方 (SIGTERM・SIGKILL・`exit`) ごとに、書きかけのファイルがどう残るか | 窓を出す本物のプロセスが要る。物差し Lifecycle (#21) が持つ |
| 実時間の時計で録ったときの実効の fps | `mokume run` から決まった fps で書き出す口が無い (mokume#1282)。入ってから測る |
| 数十時間回した後の時刻の衝突 | 長時間の運転は #25 が持つ |

## どの mokume で測ったか

**`Package.resolved` が固定している版がそのまま答えで、コミットしてある** (`v0.11.2` =
`9539162`)。`from: "0.11.2"` は他の物差しと同じく記録であって、留め金ではない。

`v0.14.0` (`34ba2d8`) へ上げた (2026-09-29)。#1626 が直り、「約束どおりだったもの」の表へ移した。

版を上げたら `swift test` を回す。**赤くなったテストは、直った約束である。**
