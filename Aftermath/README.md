# Aftermath — mokume v0.11.2 で「失敗を起こした後」のフレームを突く

**作品ではなく物差しである。** 他の物差しが「約束どおりに描けるか」を見るのに対し、こちらは
**失敗を起こした後の絵が、失敗を起こさなかったときと同じか**を見る。

途中のフレームで、次のような失敗を起こす。

- 資源の生成が投げる
- フレームの途中で放り出す
- 数でない値を渡す

その後のフレームを、失敗を起こさなかった参照と画素で比べる。

失敗の後に次のフレームが汚れる類のバグは重い。1 度踏むと、その後の絵がずっと、または
しばらく崩れるからである。mokume ではこれまで、中身の読みでしか見つかっていなかった
(mokume#342・#1179・#1180・#1183・#1184)。

## 何をしているか

**候補 1 件を、同じ絵になるはずの 2 つの経路で描く。**

- **左 (`suspect`)** は、失敗のフレーム (2 枚目) で失敗を起こす。
- **右 (`reference`)** は、同じフレームで失敗を起こさない。失敗の行を抜くか、正しい行に
  置き換える。
- 失敗の後のフレームは、両方とも同じものを描く。

失敗の後の絵が食い違えば、失敗が状態を汚して次のフレームへ持ち越している。

| 確かめ方 | 何を通るか | 何で見るか |
| --- | --- | --- |
| `mokume run .` | 窓の経路。1 候補ずつ、左右に 2 経路の絵を並べる (← → で切り替える) | 目で見る |
| `swift test` | 窓を出さない経路。`SketchRuntime` を経路ごとに組み、N 枚回す | 画素を読んで数で比べる |

組み立てと比べ方は次のとおり。

- **経路ごとに別の `SketchRuntime` で回す** (Routine と同じ形)。片方の経路で起こした失敗が、
  面を分け合う隣の経路へ漏れて疑いに混ざらないようにするためである。
- **時計はフレーム番号から導かれる** (`SketchRuntime` の既定)。失敗したフレームも番号を 1 つ
  消費するので、参照も同じ枚数を回す。粒のように乱数を使う候補は、参照でも同じ回数だけ
  乱数を消費させる。
- **比べるときの許容はほぼ 0 にする** (成分の差 0.004 = 表示の 1 段未満)。同じ機械・同じ
  フレーム番号からはバイト単位で同じ絵が出る約束 (mokume ADR-0001 原則 2) があるためである。
- **各検査は、比べる前に参照の側が描けていることを押さえる。** 参照まで何も出ていないと、
  左右が一致しても何も言えない。

候補の定義は [`Sources/Aftermath/Mishaps.swift`](Sources/Aftermath/Mishaps.swift) の 1 か所に
あり、窓もテストも同じ定義を描く。ランタイムそのものや書き出しを失敗させる 3 件は、テスト
だけに置いた ([`Tests/AftermathTests/AftermathTests.swift`](Tests/AftermathTests/AftermathTests.swift))。

## 走らせる

```bash
mokume run .                              # 窓で並べて見る
swift test                                # 窓を出さずに回して、画素で比べる
AFTERMATH_DUMP=/tmp/aftermath swift test  # 比べた最後の絵を PNG で書き出す
```

**`swift test` は緑で終わる。** 破れていたものは `withKnownIssue` で包んであり、
「既知の問題」として数えられる (`v0.11.2` では 16 本のテストで 4 件)。

**mokume 側で直ると赤くなる。** 版を上げて直ったものがあると、そのテストは
「Known issue was not recorded」で落ちる。そのときは包みを外し、下の表を書き換える。

## 結果 — mokume `v0.11.2`

**16 件を突いて、2 件が約束を破っていた。**

### 破れていたもの

| 鍵 | 何が起きたか | mokume |

`openShape`・`offFrameGraphics`・`shapeLeak` は mokume に既知の Issue がある (#1591・#1592・
#1607)。どれも「開いたままの状態に、外の `vertex()` や描き直しが紛れ込む」という事象である。
この物差しでは、**次のフレームを正しく書いた (`beginShape()` から書き直す・`beginDraw()` の
中で描く) 場合には、画素に漏れない**ことを確かめた。メモリの側は Soak が見ている。

## どうやって当たりを付けたか

mokume `v0.11.2` の公開 API から、**外のパッケージとして使うスケッチが意図して起こせる
失敗**を洗い出した。`Sketch.draw()` は投げられないので、失敗は次の 3 系統に分かれる。

1. **資源の生成が型のついたエラーを投げる。** スケッチが `try?` で握る。
2. **フレームの途中で放り出した状態。** 閉じない形・`endDraw()` の無い描き場所・`pop()` の無い `push()`。
3. **検めずに通した値。** NaN・無限・焼き場のあふれ。

そこから、公開の口だけで画素から判定できるものを選んだ。約束の出典 (ADR・説明文) が
書かれているものに限っている。

### 当たりを付けたが突かなかったもの

| 当たり | 突かなかった理由 |
| --- | --- |
| GPU が投入を打ち切ったとき、投入の後に確定させた記帳 (影の焼き付けの指紋・書き戻しの印) が「済んだ」まま残る | GPU を故意に詰まらせる必要があり、機械ごと巻き込む。mokume#1065 の完了条件も故意のハングを禁じている。**外から起こせない失敗なので、mokume 側のテストの守備範囲として戻す** (probes ADR-0006) |
| `emit` の速さや範囲に無限を渡す | 参照の側で、乱数の消費を揃えたまま「正しい行」を書く形が定まらない。`particleNaNForce` (mokume#1623) と同じ受け口の話として、Issue に書き添えた |
| 粒の力を 8 個積んだまま `particles()` を呼ばずに抜ける | 上限を超えた力を捨てるのは説明どおりで、どちらを期待とするかが説明から一意に決まらない |
| 本体の `draw()` の中で `canvas.endDraw()` を呼ぶ | 使い方の誤りで、約束の範囲の外 |
| 落ちる口 (巨大な `textSize`・`createShape` の中の `background` など) | 画素ではなくプロセスの終わり方で判定する類で、Soak が持つ (mokume#1587–#1590) |

## どの mokume で測ったか

**`Package.resolved` が固定している版がそのまま答えで、コミットしてある** (`v0.11.2` =
`9539162`)。`from: "0.11.2"` は他の物差しと同じく記録であって、留め金ではない。

版を上げたら `swift test` を回す。**赤くなったテストは、直った約束である。**
